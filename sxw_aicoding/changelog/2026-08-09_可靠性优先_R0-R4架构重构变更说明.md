# 可靠性优先 R0–R4 架构重构变更说明

> - 变更日期：2026-08-09
> - 变更提交：`93355d3ea841`（执行重构）
> - 对比基线：`30f086be7358`（架构讨论）
> - 变更规模：156 个文件，新增 28,952 行，删除 2,250 行
> - 变更性质：不保留旧接口和旧数据兼容的一次性架构切换
> - 目标定位：单机、本地磁盘、可恢复、可验证的可靠 Agent Runtime 参考实现

---

## 1. 变更摘要

本次改动落实了《可靠性优先：R1–R4 整体架构路线与 SQLite 持久化决策》，将原先由单次 HTTP 流式请求直接驱动的 Agent，重构为以 SQLite 为权威事实源、API 与执行 Worker 分离、可持久受理和恢复的 Canonical Runtime。

改造后的主链路为：

```text
Client
  → 上传 Artifact（可选）
  → POST /api/v1/runs（事务提交后 durable accepted）
  → local_storage/runtime/runtime.db
  → 独立 Runtime Worker
  → RunCoordinator
  → 每个 Run 指定的 Engine Adapter
  → Tool Broker / Artifact / ARAG / Skill / A2A
  → committed Canonical Events
  → GET events：SSE replay + tail
```

最终结果不是对原 `/chat/stream` 实现增加几张表，而是完成了以下所有权切换：

- Run 生命周期由 Runtime Store 裁决，不再由 HTTP generator、SSE 断开、`done` 或生成器 EOF 裁决。
- Conversation 语义历史由已提交 Canonical Event 编译，不再以 ADK Session 或 native HistoryStore 为事实源。
- Tool 调用由持久 ToolExecution 账本裁决，支持稳定身份、effect 分类、fencing、reconcile 和人工处置。
- Artifact 由内容寻址文件系统与 SQLite metadata/link 共同管理，不再依赖进程内 Artifact。
- ARAG 的 Document、Version、Chunk 和 IndexJob 进入 `rag.db`；vector/BM25 降为可重建投影。
- Citation 从已提交 EvidenceSet 和最终回答确定性生成，并与成功 terminal 原子提交。
- Trace 只承担诊断职责，关闭、损坏或删除 trace 均不影响恢复。

## 2. 变更背景

### 2.1 项目长期前提

本项目用于个人学习、技术方案验证和面试准备，不承担真实线上流量。本次改造遵循以下长期原则：

- 不保留旧 API、旧数据和旧实现的兼容层；
- 不建设灰度双写、shadow read 或旧表回读；
- 旧所有权不合理时直接删除；
- “生产级”重点落在状态、事务、恢复、失败语义和验收，而不是无条件增加基础设施；
- 第一阶段聚焦单机可靠执行，不宣称多机高可用。

### 2.2 改造前的主要问题

#### 2.2.1 HTTP、Agent 执行和 SSE 共用一个生命周期

旧链路在 `agent/api/chat.py` 的 `StreamingResponse` generator 内直接串联 Engine、Citation、Trace 和 SSE。客户端断开可能沿生成器取消执行，系统没有 durable accepted、独立 Run 查询、跨请求 cancel/signal、重启恢复和事件重放。

#### 2.2.2 缺少独立 Run 与持久状态机

旧 `RunContext` 没有稳定的 `run_id`、`turn_id`、幂等键、deadline、revision、release fingerprint、checkpoint 和 terminal。执行完成主要依赖易失的流事件和函数返回。

#### 2.2.3 `done`、`error` 和 EOF 被错误地用于终态推导

`StreamEvent` 同时承担 Engine 内部事件和 SSE DTO。异常可能被合并层转换成 `error` 后吞掉，而引擎又继续输出 `done`；生成器自然退出也可能被解释为成功。该模式无法证明 terminal 唯一，也无法区分“输出结束”和“Run 成功提交”。

#### 2.2.4 同一事实存在多套内存权威

改造前同时存在：

- ADK `InMemorySessionService`；
- native `HistoryStore`；
- plan_execute 局部 plan；
- ADK `tool_context.state`；
- native request-local `tool_state`；
- `InMemoryArtifactService`；
- 请求内 CitationInjector 和 trace tap。

这些对象在重启后丢失，且对“下一轮历史”“计划状态”“工具结果”“附件内容”等问题给出相互重叠的答案。

#### 2.2.5 Tool 副作用没有持久执行账本

系统无法可靠回答 Tool 是否已派发、外部副作用是否成功、ACK 是否丢失、是否允许重试、应复用哪个结果，也无法在 cancel、deadline、Worker 丢失之间给出确定结论。

#### 2.2.6 Artifact、Evidence 和 RAG 文档生命周期不完整

- Artifact 只在内存中存在，重启即丢。
- 大 Tool 结果只能截断，没有稳定 ArtifactRef。
- ARAG vector/BM25 顺序双写，缺少 DocumentVersion 和 active pointer。
- 文档缩短后可能残留旧 chunk。
- Citation 缺少 document/index version、hash、page/span、scope 和 evidence identity。

#### 2.2.7 缺少可靠性自动化门禁

项目原先以 `py_compile` 和真实 LLM 行为评测为主，缺少针对幂等、事务回滚、lease、fencing、ACK 丢失、SSE 断流、Artifact 篡改和索引恢复的确定性测试。

## 3. 目标与非目标

### 3.1 本次目标

1. 建立单一、持久、可查询的 Run/Activity/Event/Checkpoint 权威模型。
2. 解耦请求接入、后台执行和事件订阅。
3. 让三个 Engine 共用同一 Runtime 契约，同时诚实保留不同恢复粒度。
4. 为 Tool 副作用、Artifact、Evidence、Release 和 RAG 文档建立可恢复边界。
5. 通过确定性测试和故障注入证明可靠性，不依赖真实 LLM 行为得分作为门禁。
6. 一次性删除旧事实源和旧协议，防止双写重新出现。

### 3.2 明确不包含

- 旧 Session、旧 embedding、旧历史和旧 API 的数据迁移或兼容。
- Semantic、Episodic、Procedural Memory。
- 完整 Context Compiler。
- 服务端 SSE Delivery ACK 或 `delivery_cursors`。
- 多机 Worker、分布式 HA、主机/磁盘容灾。
- Temporal、PostgreSQL backend 或双写预留层。
- ADK 两代引擎的 mid-turn deterministic replay。
- Claude SKILL Artifact 跨 Skill 传递和子 Runner HITL。
- provider token 级、逐字节相同的流式重放。

## 4. 总体改动方案

### 4.1 分层结构

新增的 Runtime 按领域、应用、端口、适配器和 Worker 分层：

```text
agent/runtime/
  domain/       领域模型、状态机、错误与不变量
  application/  admission、coordinator、event、release、tool broker
  ports/        store、engine、artifact、clock、tool、release 端口
  adapters/     SQLite、Artifact、三引擎、release、brokered tools
  api/          runs、events、cancel、signals、artifacts
  worker/       dispatcher、lease、heartbeat、recovery
```

ARAG 新增持久事实和投影边界：

```text
arag/
  persistence/  rag.db、DocumentVersion、IndexJob、active pointer
  projection/   immutable numpy/BM25 snapshot 与自愈重建
```

可靠性规格和自动化门禁分别位于：

```text
docs/reliability/
tests/reliability/
scripts/check.sh
```

### 4.2 关键技术决策

- 使用 `aiosqlite + 显式 SQL`，不引入 ORM 或 Alembic。
- SQLite 写事务使用短 `BEGIN IMMEDIATE`，事务内禁止 LLM、Tool、RAG、Skill、文件系统和人工等待。
- 每个连接启用 WAL、`synchronous=FULL`、foreign keys 和 busy timeout。
- `engine` 是每个 Run 的必填冻结字段，不再使用启动期 `ENGINE` 选择主引擎。
- 一个 API 进程和一个 Worker 进程可共同支持 `plan_execute`、`agent_loop`、`native_loop`。
- SSE 只读取已提交事件，客户端 cursor 为单调 opaque seq。
- 同一 conversation 同时最多一个非终态 Run。
- Artifact 先上传，再以 `attachment_refs` 创建 Run。
- Tool effect 必须先分类，再决定重试、reconcile 或人工处置。

## 5. 分阶段实施结果

### 5.1 R0：冻结可靠性规格

新增 `docs/reliability/`，形成代码实现前的规范性裁判：

- State Ownership Registry：冻结 Runtime、Document、Artifact、Trace 的权威边界。
- Run、Activity、ToolEffect 状态机和非法迁移错误码。
- admission、event seq、checkpoint、tool、artifact、finalize 事务边界 ADR。
- streaming commit、SQLite authority、engine recovery、release compatibility ADR。
- 权威序列化边界 ADR。
- cancel/complete、ACK 丢失、lease 过期、signal 迟到、deadline 等 Failure Matrix。
- 30 个 REL 可靠性目标和 12 个 FI 故障注入点。
- RuntimeEnvelope、CanonicalEvent、WorkingState、ToolResult、Artifact、Evidence 六份 JSON Schema v1。

Delivery v1 被明确收敛为：只承诺事件已经 committed/AVAILABLE，客户端通过 `after_seq` 或 `Last-Event-ID` 重放；不承诺 DELIVERED/ACKED。

### 5.2 R1：Canonical Runtime 外壳

#### Runtime SQLite

新增 `local_storage/runtime/runtime.db`，核心事实包括：

- `schema_migrations`
- `conversations`
- `release_manifests`、`active_releases`
- `runs`、`run_requests`
- `activities`
- `run_events`
- `checkpoints`
- `tool_executions`
- `artifact_metadata`、`artifact_links`
- `signals`、`cancellation_commands`
- `timers`
- `runtime_workers`

数据库约束实现了：

- 幂等范围 `(principal_id, agent_id, idempotency_key)` 唯一。
- 同一 conversation 只允许一个非终态 Run。
- `(run_id, seq)` 唯一，event 插入和 `next_seq` 更新同事务，回滚不留洞。
- 每个 Run 最多一个 `RUN_TERMINATED`。
- `run_events` append-only，禁止 UPDATE/DELETE。
- migration version/checksum fail-fast。

#### Admission

创建 Run 的同一事务内完成：

- 幂等 request digest；
- conversation 创建或 turn 分配；
- RuntimeEnvelope 冻结；
- Run 与首个 Activity；
- `USER_MESSAGE_COMMITTED` 和状态事件；
- 输入附件的 `INPUT_ATTACHMENT` provenance link。

同 key、同 digest 返回原 Run；同 key、不同 digest 返回 `IDEMPOTENCY_KEY_REUSE`；真正的新 Run 才参与 conversation busy 竞争。

#### API 与 Worker 分离

最终进程拓扑为四个服务、至少五个进程：

```text
a2a_service :8300
skillcenter :8200
arag        :8100
Runtime Worker
agent API   :8000
```

API 不直接执行 LLM 或远程 Tool；Worker 负责 release 注册、claim、lease、heartbeat、timer、recovery 和 Engine 执行。

#### Canonical Event 与 SSE

Canonical Event 增加稳定的 `event_id/run_id/turn_id/activity_id/seq/schema_version/producer/visibility/sensitivity/terminal_status/release_fingerprint`。

SSE 遵循先 commit、后读取：

- `OUTPUT_DELTA_COMMITTED → text`
- `TOOL_CALL_COMMITTED → tool_call`
- `TOOL_RESULT_COMMITTED → tool_result`
- `MODEL_PLAN_UPDATED → plan_step`
- `SKILL_UI_FRAME_COMMITTED → skill_event`
- `CITATION_SET_COMMITTED → citation`
- `RUN_STATUS_CHANGED → run_status`
- `RUN_TERMINATED → terminal`

不再发送 `done`。SSE 断开只关闭订阅，不取消 Worker；重放遇到 terminal 后关闭连接。

#### Engine Adapter 契约

旧 `ReasoningEngine.run_stream() -> StreamEvent` 的终态职责被替换为：

```text
EngineAdapter.execute(EngineRunRequest, RuntimeIO) -> EngineOutcome
```

EngineOutcome 只能是：

- `COMPLETED`
- `RETRYABLE_FAILURE`
- `TERMINAL_FAILURE`
- `WAITING_INPUT`
- `CANCELLED`

Engine 只报告 outcome，不提交 Run terminal。`done`、`error`、EOF 和生成器正常退出均不能裁决成功；真实引擎只有在自己的成功控制分支显式设置 outcome，缺失时 fail closed 为 `ENGINE_OUTCOME_MISSING`。

#### 三引擎接入

- `plan_execute`：Model Plan 进入 WorkingState/Event，attempt 恢复时不重新规划。
- `agent_loop`：整个 ADK invocation 是粗粒度恢复 Activity；ADK Session 每 attempt 临时创建。
- `native_loop`：接入 kernel checkpoint，可从模型/工具边界恢复。

Conversation history 从 Canonical Event 编译：保留所有已提交用户消息，只纳入成功提交的 assistant message，失败 partial delta 不进入下一轮语义历史。

### 5.3 R2A：Tool Broker 与 Artifact

#### ToolManifest 与 effect 分类

统一 ToolManifest 描述 name、release digest、effect class、timeout、attempt、幂等、reconcile、cancel、结果策略和并发安全属性。

核心 effect 分类：

- `READ_ONLY`
- `IDEMPOTENT_EFFECT`
- `NON_IDEMPOTENT_EFFECT`
- `UNKNOWN_EFFECT`

未声明能力的 Skill/A2A/Claude SKILL 按 UNKNOWN 处理，不能透明自动重试。

#### ToolExecution 账本

Tool 执行采用三段式协议：

```text
短事务：Activity + ToolExecution(PREPARED) + TOOL_CALL event
事务外：执行 Tool 或 reconcile hook
短事务：effect/result + TOOL_RESULT event + Activity transition
```

实现的关键不变量：

- ToolExecution 使用由 `run_id + logical_key` 派生的稳定身份。
- ADK 完整 ToolCall batch 在执行前一次性持久化；任一 slot name/digest 漂移则整批 fail closed。
- 同 slot 的 tool name、request digest、release digest、effect class 和恢复能力必须一致。
- READ_ONLY 和稳定幂等 Tool 只在冻结语义允许时重试。
- ACK 丢失进入 UNKNOWN/RECONCILE/MANUAL，不伪装普通 failure。
- NON_IDEMPOTENT/UNKNOWN 不透明重发。
- 旧 fencing token 的 Tool 结果拒绝提交。
- cancel/deadline 在 Store 标记事务和实际外部 I/O 前双重检查。
- ToolResultEnvelope 对 SUCCESS、FAILURE、INTERRUPT、NO_OUTPUT、UNKNOWN 实施严格状态约束。
- effect status、result status、Artifact ref、event、ledger 和 link 在同一事务内保持一致。
- 外部 `external_object_id/result_ref` 跨 retry、reconcile、manual、Worker kill 和重启单调保留。

#### 人工 Tool reconciliation

新增严格 `tool_reconciliation` signal：

- `mark_committed`
- `mark_failed`
- `reconcile`

人工处置要求明确的 `tool_execution_id`、非空 evidence 和合法 ToolResult。`reconcile` 只调用查询 hook，永远不会调用原副作用 executor。

普通 Run 只有最后一个 unresolved effect 解决后才恢复；cancel 已先提交时 Run 始终保持 `CANCEL_REQUESTED`，最后一个 effect 解决后才 `CANCELLED`。hook 前、中、后 Worker 丢失均可回到受审计的 MANUAL 边界，不盲目重发副作用。

#### Artifact CAS

新增内容寻址 Artifact Store：

```text
local_storage/artifacts/sha256/<prefix>/<sha256>
```

写入顺序为 temp file → hash/size → fsync file → atomic rename → fsync directory → metadata/link transaction。

实现能力包括：

- 上传默认上限 20 MiB，内部 Artifact 默认上限 100 MiB。
- 模型默认预览 8 KiB；`read_artifact` 默认 32 KiB、最大 64 KiB。
- HTTP Range 单次最大 1 MiB。
- 每次读取前校验 digest，篡改返回 `ARTIFACT_INTEGRITY_ERROR`。
- 同 digest 的 media type/storage key 漂移 fail closed。
- metadata/link 事务失败只留下可清理 orphan。
- 跨进程锁保护 publish、read 和 orphan cleanup 竞态。
- 图片附件由 Worker 从已校验 CAS 物化为 attempt-local 多模态输入。
- 大 Tool 结果在 Event、Checkpoint 和 Trace 中只保存有界 preview/ref。

### 5.4 R2B：Document、Index 与 Evidence

#### Durable Document 与 IndexJob

新增 `local_storage/arag/rag.db`，核心表包括：

- `documents`
- `document_versions`
- `active_document_versions`
- `chunks`
- `index_jobs`
- `chunk_embeddings`
- `projection_metadata`
- `schema_migrations`

入库 API 改为异步 durable job：

- `POST /v1/index` 返回 `202 + job_ids`。
- `GET /v1/index/jobs/{job_id}` 查询状态。
- Job 状态为 `PREPARED → BUILDING → VALIDATING → READY → ACTIVATED | FAILED`。
- parse/caption/embed 在事务外执行。
- 校验 chunk、hash、embedding dim 和 projection digest 后，单事务切换 active version。
- Retrieval 只读取 active version，旧版本和残留 chunk 不再可见。
- 未完成 Job 在重启后恢复或安全重建。

#### vector/BM25 降为投影

- embedding 使用 float32 BLOB、dim、checksum 持久化。
- 进程内加载 immutable numpy snapshot。
- BM25 从 active chunks 重建。
- active pointer 切换后原子替换内存 snapshot。
- projection 删除、缺失、checksum/dim/model 异常时从 active Document/Chunk truth 重新 embed 和重建。
- 重建失败期间保留 BM25 可用并返回 DEGRADED，使用退避避免热循环。
- 原 `local_storage/embedding` 三文件路径不再是权威存储。

#### Retrieval 与 Evidence

检索状态固定为：

- `HIT`
- `MISS`
- `DEGRADED`
- `DENIED`
- `ERROR`

RetrievalContext 透传 query、run、activity、principal、scope、dataset 和绝对 deadline。deadline 过期时不启动 rewrite/embed/retrieval；在途超时会取消子协程并稳定返回 `DEADLINE_EXCEEDED`。

完整 EvidenceSet 保存为 Artifact，包含 document/index version、content hash、page/span、scope、query 和 evidence_id；模型只看到有界 hits preview。

Citation 不再由请求内 CitationInjector 裁决，而是根据 committed EvidenceSet 和最终 assistant message 确定性生成。`ASSISTANT_MESSAGE_COMMITTED + CITATION_SET_COMMITTED + SUCCEEDED terminal` 在同一个 SQLite 事务中提交。

### 5.5 R3：native_loop 长任务闭环

native_loop 新增 `native-kernel-v1` checkpoint，在以下边界提交：

- model request 前；
- 完整 ToolCall batch 后；
- 每个 ToolResult 后；
- compact boundary；
- next-turn；
- completed/stop transition。

半个 model stream 崩溃时重放该 model slot；已经提交的 ToolExecution 按稳定 slot 复用。只读 Tool 可在完整、安全的流式调用边界提前执行；side-effect/UNKNOWN 必须等待完整 ToolCall batch 提交。

新增确定性 `/reliability-demo` 纵切，覆盖：

```text
StartRun
→ slow_lookup 两次 retryable failure
→ checkpoint WorkingState
→ request_input
→ WAITING_INPUT
→ signal approval
→ 独立 effects.db 中创建幂等 demo task
→ Artifact/Evidence
→ final answer + SUCCEEDED
```

Worker 通过 lease、续租、fencing、timer CAS 和 recovery scan 恢复；Worker 丢失不直接把 Run 判为 FAILED。

### 5.6 R4：所有权一次性切换

删除或降级的旧实现：

- 删除 `POST /api/v1/chat/{agent_uuid}/stream` 及 `agent/api/chat.py`。
- 删除全局 ADK SessionManager。
- 删除 native HistoryStore 和请求级历史写回。
- 删除旧内存 ArtifactService。
- 删除请求内 CitationInjector 的权威职责。
- 删除 request-local trace tap 对执行生命周期的影响。
- 删除 `StreamEvent.done/error` 和 EOF 终态推导。
- 删除 vector/BM25 作为 Document truth 的路径。
- 删除启动期主引擎 `ENGINE` 选型。

ADK Session、InMemoryArtifact 和 request-local tool_state 只允许作为单次 adapter/attempt 的临时对象，函数返回后销毁，不能参与恢复裁决。

Web UI 改为：上传 Artifact → 创建 Run → 保存 `run_id/last_seq` → SSE 自动重连。停止观看只关闭订阅，取消运行显式调用 cancel API。页面重载若没有本地 UI 投影会从 seq 0 完整重放，避免只恢复 suffix。

eval client 改为 create → subscribe → GET status，以 terminal 状态判断完成，不再依赖 `done`。行为评分继续记录，但不作为可靠性门禁。

`scripts/run_all.sh` 改为：

- 下游先启动；
- Runtime Worker 注册三个 active release 并产生 fresh heartbeat；
- 样本索引 Job 全部 ACTIVATED；
- 最后启动 Agent API；
- 五个子进程全程监督并统一停机、回收；
- 兼容 macOS Bash 3.2；
- 环境变量优先、`.env` 次之，密钥占位符启动前 fail-fast。

## 6. 最终公开接口

### Runtime API

| 方法 | 路径 | 结果 |
|---|---|---|
| `POST` | `/api/v1/artifacts` | 上传内容寻址 Artifact，成功返回 201 |
| `GET` | `/api/v1/artifacts/{artifact_id}` | 校验 digest 后读取，支持受限 Range |
| `POST` | `/api/v1/runs` | 幂等创建 Run，事务提交后返回 202 |
| `GET` | `/api/v1/runs/{run_id}` | 查询状态、revision、当前 Activity、pending input、terminal、last_seq |
| `GET` | `/api/v1/runs/{run_id}/events` | committed SSE replay/tail，支持 `after_seq` 和 `Last-Event-ID` |
| `POST` | `/api/v1/runs/{run_id}/cancel` | 幂等显式取消 |
| `POST` | `/api/v1/runs/{run_id}/signals` | 幂等 HITL 或 Tool reconciliation signal |

CreateRun 必须携带 `Idempotency-Key`，body 中必须指定：

```json
{
  "client_request_id": "client UUID",
  "conversation_id": null,
  "principal_id": "demo-user",
  "agent_id": "demo-agent",
  "engine": "native_loop",
  "input": {
    "text": "用户问题",
    "attachment_refs": []
  },
  "deadline_at": "2026-08-09T10:00:00Z"
}
```

允许的 `engine` 为 `plan_execute | agent_loop | native_loop`。未注册 active release 时返回 `NO_ACTIVE_RELEASE`；conversation 已有活动 Run 时返回 `CONVERSATION_BUSY`。

## 7. 关键可靠性语义

### 7.1 Run、cancel 与 terminal

- terminal 事务先提交：后续 cancel 返回 `RUN_ALREADY_TERMINAL`。
- cancel CAS 先提交：迟到执行结果可审计，但不能覆盖为 SUCCEEDED。
- cancel 时存在 DISPATCHED/UNKNOWN effect：保持 `CANCEL_REQUESTED`，完成 reconcile 后才进入 `CANCELLED`。
- unresolved effect 到 deadline：Run 为 `TIMED_OUT`，terminal payload 保留 unresolved IDs。
- final assistant、citation 和 SUCCEEDED terminal 原子提交。

### 7.2 Lease 与 fencing

- claim 使用原子 UPDATE/RETURNING 和稳定排序。
- lease 过期只触发分类恢复，不直接判失败。
- reclaim 后旧 fencing token 对 event、checkpoint、Tool settle 和 terminal 都失效。
- Worker heartbeat 只作运维观察，恢复事实仍以 Activity lease 为准。

### 7.3 Signal

- 同 signal id、同 digest 返回原结果；不同 digest 返回冲突。
- terminal Run 的迟到 signal 写入 `REJECTED_LATE` 审计并返回 409。
- WAITING_INPUT 跨 Store/Worker 重启后仍可继续。
- generic signal 不能覆盖 Tool reconciliation 边界。

### 7.4 Release 与 Schema

- release manifest 使用规范化 JSON + SHA-256。
- fingerprint 覆盖 Engine、共享 Runtime、Tool/Skill/A2A catalog 和无密钥语义配置。
- release/schema 精确匹配可直接恢复。
- 显式 upgrader 在事务外纯转换，Store 以 fence + checkpoint revision CAS 原子发布升级 checkpoint。
- 无 upgrader、错误 key、错误 engine、转换异常或旧 fence 均 fail closed 为 `INCOMPATIBLE_RELEASE`。

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 受理 | HTTP 流连接即执行 | POST 事务提交即 durable accepted |
| 执行 | 请求 generator 内 | 独立 Runtime Worker |
| Run | 无独立持久实体 | Run/Activity/Checkpoint/Terminal 状态机 |

| 客户端断流 | 可能取消执行 | 只停止观看，不影响 Run |
| Tool | 内存调用与日志 | 持久 ToolExecution/effect ledger |

## 11. 升级与运行影响

### 11.1 不兼容变化

- 旧 `/api/v1/chat/{agent_uuid}/stream` 已删除。

## 12. 最终结论

本次变更已完成从“请求驱动的流式 Agent Demo”到“单机持久化可靠 Agent Runtime 参考实现”的主架构切换。

最终系统已经能够证明：

- 请求只创建一个 Run，幂等冲突有确定语义。
- HTTP/SSE 断开后 Run 继续执行。
- API 或 Worker 重启后可从 committed boundary 恢复。
- SSE 可从任意可见 cursor 无丢失、无重复重放。
- assistant message、citation 和成功 terminal 原子提交。
- cancel、deadline、late result 和 Tool complete 竞态有唯一结论。
- ACK 丢失不会导致未知副作用被盲目重发。
- WAITING_INPUT 不占 Worker，重启后仍可由 signal 恢复。
- Artifact 和 Evidence 可校验、可追溯。
- 文档缩短后旧 chunk 不可检索，vector/BM25 删除或损坏后可重建。
- 清空 ADK/native 内存状态后仍可编译下一轮上下文。
- 三代引擎共用一个 Runtime，同时保留并文档化各自恢复粒度。
- Trace 关闭、写入失败或文件删除不影响恢复结果。

该版本的可靠性边界是“单机 SQLite + 本地磁盘”。它已经建立了清晰的权威状态、事务和失败模型，但不应被描述为多机高可用或跨主机容灾系统。
