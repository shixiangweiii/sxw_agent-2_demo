# 集群化部署改造评估

## 一、评估背景

当前架构为单机多进程部署（四服务五进程），基于本地 SQLite、本地文件系统和本机进程协调。本文档评估将该架构迁移到多机器集群环境时，需要改造的关键点、技术挑战和方案选型。

**诚实边界声明**：本文档不包含具体实现细节，仅用于技术方案评估和架构决策参考。

---

## 二、核心改造点

### 2.1 存储层改造

#### 2.1.1 runtime.db（SQLite → 分布式关系数据库）

**现状**
- 单文件 SQLite，WAL 模式，`synchronous=FULL`
- 承担 Run/Event/Activity/ToolExecution/Checkpoint 等核心状态
- 所有写操作使用短 `BEGIN IMMEDIATE` 事务
- `runs.next_seq` 与 event batch 同事务更新，保证无空洞

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 并发写入 | SQLite 单写者模型 vs 分布式数据库多写者并发 |
| 事务语义 | 短事务内的 LLM/Tool 调用禁止 → 分布式事务的延迟和死锁风险 |
| 序列号生成 | `next_seq` 的单调递增和无空洞要求需要分布式序列方案 |
| 一致性级别 | 当前强一致 → 集群下需要权衡延迟和可用性 |
| 迁移路径 | 从 SQLite 到 PostgreSQL/CockroachDB 的 schema 迁移 |

**方案选型**
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| PostgreSQL + 主从 | 成熟稳定，运维成本低 | 主从切换有短暂不可用 | 中小规模，对延迟敏感 |
| CockroachDB/TiDB | 原生分布式，自动分片 | 运维复杂，资源消耗高 | 大规模，高可用要求 |
| 分库分表 | 水平扩展能力强 | 跨分片事务复杂 | 数据量极大，可容忍分片键限制 |

**关键决策**
- Event append 的原子性必须保证：`runs.next_seq` 更新 + event batch 插入必须在同一事务
- Checkpoint 的 revision CAS 需要乐观锁或分布式锁
- 考虑引入分布式序列生成器（Snowflake/DB sequence）替代自增 `next_seq`

---

#### 2.1.2 Artifact CAS（本地文件 → 共享对象存储）

**现状**
- SHA-256 命名的本地文件存储
- 写入流程：temp → digest/size → fsync → atomic rename → fsync dir
- 读取边界：非图片 8KiB preview，`read_artifact` 默认 32KiB/最大 64KiB
- HTTP 单 Range 最大 1MiB

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 原子性写入 | `atomic rename` 在分布式 FS 上不一定原子 |
| 并发去重 | 多节点同时上传相同 digest 的 CAS 语义 |
| 读取一致性 | 写入后可见性保证 vs 对象存储的最终一致 |
| 性能 | 对象存储的延迟 vs 本地文件系统 |
| 成本 | 对象存储的流量和存储成本 |

**方案选型**
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| S3/OSS | 成熟，成本低，天然分布式 | 延迟较高（100ms+），无原子 rename | 大多数场景 |
| 分布式 FS (Ceph/GlusterFS) | 语义接近本地 FS | 运维复杂，资源消耗高 | 对延迟和语义要求高 |
| 本地缓存 + 对象存储 | 读性能接近本地 | 缓存一致性复杂，需要失效策略 | 读多写少场景 |

**关键决策**
- CAS 写入的原子性需要分布式锁或 CAS 原语（如 S3 的 `If-None-Match`）
- 考虑分层存储：热数据本地 SSD，冷数据对象存储
- Range 请求需要支持对象存储的分片下载

---

#### 2.1.3 rag.db（SQLite → 共享存储 + 分布式向量库）

**现状**
- SQLite 存储 documents/chunks/embeddings 等元数据
- numpy vector + BM25 是进程内不可变投影
- 检索只读 active version
- Evidence 带 document/index version、content hash、page/span

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 元数据存储 | SQLite → 分布式数据库迁移 |
| 向量检索 | 进程内 numpy → 分布式向量数据库 |
| 索引构建 | 单进程 index job → 分布式任务队列 |
| Active version 切换 | 单事务 pointer 切换 → 分布式协调 |
| 降级语义 | `DEGRADED` 状态的检测和恢复 |

**方案选型**
| 组件 | 方案 | 说明 |
|---|---|---|
| 元数据 | PostgreSQL | 与 runtime.db 共用或独立实例 |
| 向量检索 | Milvus/Qdrant/Weaviate | 支持分布式索引和近似搜索 |
| BM25 | Elasticsearch/Meilisearch | 或集成到向量库的混合检索 |
| 索引任务 | Celery/Temporal | 分布式任务队列 |

**关键决策**
- 向量库和元数据的一致性问题：chunk 写入成功后再更新向量库
- Active version 的切换需要原子性保证（metadata + vector index pointer）
- 考虑向量库和对象存储的集成（如 Qdrant 支持 S3 backend）

---

#### 2.1.4 local_storage（文档原文存储）

**现状**
- 本地文件系统 `local_storage/arag/documents/sha256/`
- 文档原文按 SHA-256 存储

**改造方案**
- 迁移到对象存储（S3/OSS），key 为 SHA-256
- 保留本地缓存层，LRU 淘汰策略
- 需要考虑大文件的分片上传和断点续传

---

### 2.2 进程协调改造

#### 2.2.1 Worker Activity 领取（本地 lease → 分布式锁）

**现状**
- Worker 使用 lease/revision/fencing 领取 Activity
- SQLite 短事务保证领取的原子性
- 旧 fencing 结果拒绝，Worker 丢失不直接失败 Run

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 分布式锁 | 多节点竞争同一 Activity 的互斥 |
| Lease 续约 | 网络分区下的 lease 续约和故障转移 |
| Fencing token | 全局单调递增的 token 生成 |
| 恰好一次语义 | 保证 Activity 不被重复执行 |
| 崩溃恢复 | Coordinator/Worker crash 后的状态恢复 |

**方案选型**
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| etcd | 强一致，支持 watch | 运维成本，资源消耗 | 对一致性要求高 |
| ZooKeeper | 成熟稳定 | 运维复杂，CP 模型 | 已有 ZK 集群 |
| Redis Redlock | 性能高，部署简单 | 争议性算法，时钟依赖 | 对性能要求高，可容忍小概率重复 |
| 数据库锁 | 简单，无额外依赖 | 性能瓶颈，单点风险 | 小规模，快速迁移 |

**关键决策**
- 推荐使用 etcd 或 ZooKeeper，保证强一致性
- Fencing token 需要全局单调递增（etcd 的 revision 或 ZK 的 zxid）
- 考虑 Activity 的幂等性设计，允许安全重试

---

#### 2.2.2 Heartbeat 检测（单进程 → 集群感知）

**现状**
- Worker 启动时验证 `ACTIVE` heartbeat 和三种 active release pointer
- 单进程 heartbeat 无法跨节点感知

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 存活检测 | 区分"进程存活"和"任务进度" |
| 故障转移 | 节点故障后的 Activity 重新分配 |
| 脑裂防护 | 网络分区下的多活问题 |
| 优雅下线 | Rolling update 时的 Activity 迁移 |

**方案设计**
- Heartbeat 写入分布式 KV（etcd/Redis），带 TTL
- 独立的 Health Checker 进程监控和故障转移
- 区分两种语义：
  - **进程存活**：定时续约 heartbeat
  - **任务进度**：Activity 级别的进度上报，用于断点续跑

---

#### 2.2.3 RunCoordinator 分布式化

**现状**
- 单进程 RunCoordinator 管理 EngineAdapter 执行
- Engine outcome 是 Coordinator 输入，不得根据内部事件推导 terminal
- Run terminal 最多一个，只有 RunCoordinator 能提交 terminal

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 单点 Coordinator | 多节点下需要保证同一 Run 只有一个 active Coordinator |
| Coordinator 崩溃 | 崩溃后新 Coordinator 如何恢复执行 |
| Terminal 提交 | 多节点竞争 terminal 提交的互斥 |
| 状态同步 | Coordinator 和执行 Engine 的状态一致性 |

**方案设计**
- 每个 Run 分配一个 Coordinator，使用分布式锁保证互斥
- Coordinator 定期 checkpoint 执行状态到分布式存储
- 崩溃后新 Coordinator 从最后 checkpoint 恢复
- Terminal 提交使用 CAS（如 `UPDATE runs SET status='TERMINATED' WHERE id=? AND status != 'TERMINATED'`）

---

### 2.3 状态同步改造

#### 2.3.1 SSE 订阅（本地 event → 跨节点 event 分发）

**现状**
- SSE 从 committed `run_events` 短查询 replay/tail
- 支持 `after_seq` 和 `Last-Event-ID`
- Commit 后 SSE 可见，visibility 可造成 seq 跳号

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 事件分发 | 多 API 节点需要感知所有 event |
| 顺序保证 | 跨节点的事件顺序和单调递增 seq |
| 连接亲和 | 客户端可能连接到不同 API 节点 |
| 重放一致性 | 多节点 replay 的结果一致性 |

**方案选型**
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| Kafka/Pulsar | 高吞吐，持久化，顺序保证 | 运维复杂 | 大规模，对延迟不敏感 |
| Redis Pub/Sub | 低延迟，部署简单 | 无持久化，可能丢消息 | 小规模，可容忍丢消息 |
| 数据库轮询 | 简单，无额外依赖 | 延迟高，数据库压力 | 快速迁移，对延迟要求低 |
| Sticky Session | 无需改造 | 负载均衡复杂，故障转移困难 | 短期过渡方案 |

**关键决策**
- 推荐使用 Kafka/Pulsar 作为 event bus
- Event 写入数据库后异步发布到 Kafka
- SSE 订阅从 Kafka 消费，支持 `after_seq` 的 offset 定位
- 考虑引入 CDC（Change Data Capture）工具（如 Debezium）减少代码侵入

---

#### 2.3.2 Event 序列号生成（本地自增 → 分布式序列）

**现状**
- `runs.next_seq` 与 event batch 同事务更新
- 保证 seq 无空洞

**改造挑战**
| 挑战 | 说明 |
|---|---|
| 全局单调递增 | 多节点并发写入的序列号生成 |
| 无空洞 | 事务回滚不留 seq 洞 |
| 性能 | 分布式序列生成的延迟 |

**方案选型**
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 数据库 sequence | 简单，强一致 | 性能瓶颈，单点风险 | 中小规模 |
| Snowflake | 高性能，去中心化 | 时钟回拨问题，ID 非连续 | 大规模，可容忍非连续 |
| 号段模式 | 批量获取，性能高 | 节点崩溃可能浪费号段 | 大规模，可容忍空洞 |

**关键决策**
- 如果严格要求无空洞，必须使用数据库事务
- 如果可以容忍空洞，推荐号段模式（如美团 Leaf）
- 考虑将 `seq` 拆分为 `(partition_id, local_seq)`，降低冲突

### 2.4 分布式问题处理

#### 2.4.1 脑裂防护

**问题描述**
网络分区下，多个节点同时认为自己是 leader，导致双写。

**解决方案**
- 使用 consensus 算法（Raft/Paxos）保证 leader 唯一性
- 所有写操作必须经过 leader
- Fencing token 机制：每次写操作携带 monotonic token，旧 token 拒绝

**技术选型**
- etcd/ZooKeeper 内置 consensus，可直接使用
- 数据库层面：PostgreSQL 的 Patroni、MySQL 的 MGR

---

#### 2.4.2 时钟漂移

**问题描述**
当前 deadline 是绝对 UTC，多节点时钟不同步导致 deadline 判断不一致。

**解决方案**
- NTP 同步所有节点时钟
- 引入逻辑时钟（Lamport timestamp）作为补充
- deadline 判断增加 buffer（如 ±100ms）
- 关键操作使用数据库时间戳而非应用服务器时间

---

#### 2.4.3 网络分区

**问题描述**
cancel/complete 的提交顺序在网络分区下可能不一致。

**解决方案**
- 使用分布式事务（2PC/3PC）保证原子性
- 或接受最终一致性，通过 reconcile 机制解决冲突
- 当前架构的"cancel-first"语义可以在分布式下通过 timestamp 比较实现

---

### 2.5 运维与可观测性

#### 2.5.1 配置管理

**改造点**
- 环境变量/配置文件 → 集中配置中心（Apollo/Nacos/Consul）
- 支持配置热更新和灰度发布
- 敏感配置（API Key）加密存储

---

#### 2.5.2 日志收集

**改造点**
- 本地日志 → 集中日志系统（ELK/Loki）
- 结构化日志，带 trace_id 跨服务追踪
- 日志级别动态调整

---

#### 2.5.3 监控告警

**改造点**
- Prometheus + Grafana 监控指标
- 关键指标：Run 延迟、Worker 利用率、Event 吞吐、Artifact 存储
- 告警规则：错误率、延迟 P99、资源使用率

---

#### 2.5.4 部署与发布

**改造点**
- 容器化部署（Docker + Kubernetes）
- 滚动升级策略，保证兼容性
- 数据库 migration 的在线变更
- 灰度发布和流量切分

## 三、改造优先级与路线图

### 3.1 Phase 1：存储层改造（高优先级）

**目标**：解决多节点数据共享问题

**任务**
1. SQLite → PostgreSQL 迁移
   - Schema 转换脚本
   - 数据迁移工具
   - 一致性验证
2. Artifact CAS → S3/OSS
   - 实现 S3 SDK 的 CAS 写入
   - 本地缓存层优化
3. rag.db → PostgreSQL + Milvus
   - 元数据迁移
   - 向量检索服务化

**验收标准**
- 多节点并发读写正确
- 数据一致性验证通过
- 性能基准测试达标

---

### 3.2 Phase 2：进程协调改造（高优先级）

**目标**：实现分布式任务调度

**任务**
1. 部署 etcd/ZooKeeper 集群
2. Worker Activity 领取改造
   - 分布式锁实现
   - Fencing token 集成
3. RunCoordinator 分布式化
   - 状态 checkpoint
   - 崩溃恢复机制

**验收标准**
- 多 Worker 并发领取正确
- Coordinator 崩溃后恢复成功
- 无重复执行或遗漏执行

---

### 3.3 Phase 3：状态同步改造（中优先级）

**目标**：实现跨节点事件分发

**任务**
1. 部署 Kafka/Pulsar 集群
2. Event 发布到 Kafka
3. SSE 订阅从 Kafka 消费
4. 分布式序列号生成

**验收标准**
- 事件顺序正确
- 延迟在可接受范围（<1s）
- 无消息丢失或重复

---

### 3.4 Phase 4：运维体系建设（中优先级）

**目标**：提升可观测性和运维效率

**任务**
1. 配置中心集成
2. 日志收集系统
3. 监控告警平台
4. 容器化部署

**验收标准**
- 关键指标可观测
- 告警及时准确
- 支持滚动升级和灰度发布

---

### 3.5 Phase 5：分布式问题处理（低优先级）

**目标**：提升系统的容错能力

**任务**
1. 脑裂防护机制
2. 时钟漂移补偿
3. 网络分区下的降级策略

**验收标准**
- 故障场景下系统可用
- 数据一致性不破坏
- 自动恢复能力

## 四、风险评估

### 4.1 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 分布式事务性能 | 延迟增加，吞吐下降 | 优化事务粒度，减少跨分片操作 |
| 数据一致性 | 多节点数据不一致 | 强一致方案 + 对账机制 |
| 运维复杂度 | 故障排查困难 | 完善监控和日志，SOP 文档 |
| 迁移风险 | 数据丢失或服务中断 | 灰度迁移，回滚预案 |

### 4.2 成本风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 基础设施成本 | 服务器、存储、带宽 | 容量规划，按需扩展 |
| 人力成本 | 运维和开发投入 | 自动化运维，文档沉淀 |
| 迁移成本 | 时间和资源投入 | 分阶段迁移，快速验证 |

## 五、决策建议

### 5.1 技术栈推荐

| 组件 | 推荐方案 | 备选方案 |
|---|---|---|
| 关系数据库 | PostgreSQL | CockroachDB/TiDB |
| 对象存储 | 阿里云 OSS | AWS S3/MinIO |
| 向量数据库 | Milvus | Qdrant/Weaviate |
| 协调服务 | etcd | ZooKeeper |
| 消息队列 | Kafka | Pulsar |
| 配置中心 | Nacos | Apollo/Consul |
| 容器编排 | Kubernetes | Docker Swarm |
| 监控告警 | Prometheus + Grafana | DataDog |

### 5.2 迁移策略

**建议采用"绞杀者模式"（Strangler Fig Pattern）**

1. **Phase 1**：先迁移存储层，API 层保持单节点
2. **Phase 2**：API 层水平扩展，引入负载均衡
3. **Phase 3**：Worker 集群化，分布式任务调度
4. **Phase 4**：完善运维体系，灰度发布

**关键原则**
- 每个阶段独立可回滚
- 新旧系统并行运行，逐步切流
- 充分测试，快速验证

## 七、总结

当前架构从单机迁移到集群环境，核心挑战在于：

1. **存储层**：SQLite 和本地文件系统无法满足多节点共享需求
2. **进程协调**：本地 lease/heartbeat 需要分布式锁和协调服务
3. **状态同步**：SSE 和 Event 需要跨节点分发机制
4. **分布式问题**：脑裂、时钟漂移、网络分区需要专门处理

建议采用分阶段迁移策略，优先解决存储层和进程协调问题，逐步完善运维体系。技术栈推荐 PostgreSQL + etcd + Kafka + Kubernetes 的组合，成熟稳定，社区活跃。
