## 简介说明（更新于 2026/8/12 17:10）

这是一个基于公司生产项目简化后的用于我个人学习和准备面试的项目源码，不承担真实线上流量，因此这个项目相关的改动不要受既有技术债和历史兼容包袱约束，新代码不得主动制造缺乏明确收益的技术债；

保持简洁，不需要兼容旧 API、旧行为和旧业务数据，也不要保留 schema migration 机制，也不要为了旧数据保留兼容层；
    生产级要求覆盖运行时正确性、多实例协作和故障恢复，但数据库跨版本升级、滚动发布期间的 schema 兼容和旧数据保留不在本项目范围内；
    数据库只支持当前最新schema。schema 不匹配时必须 fail-fast，并提示用户显式删除或重建对应本地数据库；程序不得静默删除、覆盖或自动迁移旧数据库。
    每次如果有更新改动，我会亲自直接把 "local_storage" 目录下所有存量数据都删除，直接用空的状态跑最新的代码，所以如上所属不要做任何的旧数据保留兼容层；

只管大胆使用最先进、最优秀、生产级的技术方案思路即可，但是需要具备生产级的思考、设计和工程素养，如生产级考虑的边界case处理、状态机设计严谨性；
    “生产级”：除边界 case 和状态机外，至少还应包含：并发竞争、幂等、超时与重试、部分失败、资源上限、背压、安全、可观测性和故障恢复；
    技术方案要先进，但必须成熟可验证、与问题匹配，并且新增复杂度有明确收益；

变量、代码、注释、文档等保持简洁直白、语义明确，尤其是代码不要故意秀语法炫技，重点在于设计方案上的先进性而不在于语法糖；
    “直白优于模式堆砌”但不是允许失控的长函数、重复逻辑和复杂分支；
    宁可选择容易理解的线性流程，也不要为了套用设计模式制造无价值的间接层；但仍需控制函数复杂度、封装稳定职责并消除实质性重复；

不要滥用设计模式优先选择可直接阅读的线性流程，不为了套用设计模式制造无价值的间接层、做好封装、做好合适层次的抽象、组合优于继承（慎用继承，继承控制在2级之内即 Base -> Sub，不允许 Base -> Middle -> Sub）；

思考设计要“生产级”（因为我面试需要能讲出来“生产级”的解决方案！），生产目标方案必须支持多实例和跨节点协作，比如一开始就要考虑实际集群化分布式，如果缺少相关中间件依赖可以提出来一起讨论
    本地开发和测试允许使用单机适配器，但不得把只能在单进程或单节点上保证正确性的实现定义为生产目标方案；
    涉及共享状态、任务调度、会话、取消、租约、幂等、副作用或进度管理的生产目标方案，必须考虑多实例和跨节点协作；
    目前使用 SQLite 的现状处理：暂时先维持现状，目前本地开发可以使用单机实现（单机多进程），但不能让进程内存成为跨进程状态的唯一权威；

对于现有历史代码暂时不做一次大改动后续慢慢小步重构即可；

对于新生成的代码要遵守以上最新的要求；
    未触及的历史代码暂不强制改造；
    本次新增或实质修改的代码路径遵守新规则；修改历史文件中的局部代码，不代表必须重构整个文件或模块；
    每次小步重构都必须独立正确、可测试；
    不能长期（临时双写或过渡适配必须有明确用途、删除条件和验证方式，不得成为最终状态）保留双写或两套语义；

最后：具体开发过程中，遇到输入的要求和此项目背景约束有冲突之处，主动提出来一起讨论；
