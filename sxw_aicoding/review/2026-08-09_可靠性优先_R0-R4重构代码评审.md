## 0. 一句话结论：**没有严重阻塞性 bug**

专门针对"阻塞性"做了实测：Worker `SIGKILL` 中断后 Run 不会永久卡死（lease 到期自动恢复、attempt/fence 递增、terminal 唯一、seq 不断裂）；Artifact CAS 锁无嵌套、无死锁、无饥饿；门禁全绿；三引擎真实 LLM 端到端全部 `SUCCEEDED`。没有发现会导致**卡死、丢 Run、数据损坏、重复副作用或状态机死锁**的问题。

已发现的最高级别问题 F-1 是**语义正确性**缺陷（引用归属错误），系统照常运行、不阻塞任何链路，但会输出错误的引用归属。

## 1. 总体结论

这次重构的**可靠性内核是可信的**。它不是"给旧 `/chat/stream` 加几张表"，而是真正完成了所有权切换：Run 生命周期、Canonical Event、Tool effect 账本、Artifact CAS、Document 版本与投影，各自只有一个裁判。状态机、事务边界、fencing、CAS 的实现密度和自洽程度，明显高于一般"演示级"项目，schema 层用 `STRICT` 表、partial unique index、append-only trigger 把关键不变量下沉到数据库，而不是只靠应用代码自律。

changelog 第 9 章的验收声明**逐条复现成立**，没有发现夸大。这一点值得单独说明：我按原样重跑了门禁和真实五进程冒烟，数字与文档完全一致。

同时发现 **1 个 P1 正确性缺陷**（引用归属被交叉相乘）和 **2 个 P2**（Evidence span provenance 是伪造偏移；Artifact 读取全量重复哈希）。P1 直接损伤本次重构主打的"Citation 可追溯到稳定 Evidence"这条能力声明——它不破坏 Run 可靠性不变量，但会让引用**指向模型并未标注的文档**。

一个重要判断：这三个问题都**不在**可靠性门禁的覆盖盲区之外——它们恰好落在"状态机之外的语义正确性"这一层。R0–R4 把"执行是否可靠"证明得很扎实，但"证据与引用是否**正确**"目前只有单条检索路径的测试覆盖。这是下一阶段最值得补的缺口。

| 维度 | 评价 |
|---|---|
| 状态机 / 事务 / fencing / CAS | 优秀，可作为参考实现 |
| 单一事实来源落实 | 优秀，旧事实源确已删除且被门禁扫描 |

| 文档诚实度 | 高；仅 1 处客户端契约未写明（F-6） |

### 2.5 Worker 崩溃恢复（阻塞性风险专项实测）

手动拉起 5 进程后，在 `native_loop` Run **执行中途**对 Worker 发 `SIGKILL`（无 graceful drain），再重启 Worker：

```text
kill 前 : run=RUNNING act=RUNNING attempt=1 fence=1 lease_owner=runtime-worker-local next_seq=9
kill 后 : run=RUNNING act=RUNNING attempt=1 fence=1  (terminal=null)
重启后  : 70s 内恢复 -> SUCCEEDED attempt=2 fence=2 lease_owner=null next_seq=204
```

逐条通过：

- Worker 丢失**没有**把 Run 判为 `FAILED`（符合规格"worker 丢失不是 FAILED"）
- 无 Worker 存活期间，API 仍能正常返回 Run 状态（API/执行确已解耦）
- lease 到期后由 `recover_expired` 重新分派，**attempt 与 fencing token 同时递增**（旧执行者被围栏隔离）
- 跨崩溃边界后：恰好一个 `RUN_TERMINATED`、恰好一个 `ASSISTANT_MESSAGE_COMMITTED`
- canonical `seq` 跨崩溃边界仍然**连续无洞**（1..203）
- 崩溃后从 seq 0 重放仍以**唯一** terminal 收尾

恢复耗时 ≈ 70s，主要是 30s lease 到期 + 第二次完整 attempt，属于配置而非缺陷（`runtime_lease_seconds` 默认 30）。

补充观察：重放会同时包含 attempt-1 的**部分 delta** 与 attempt-2 的完整输出。这是规格允许的（"失败 partial delta 可以被用户看到，但不进入后续语义历史"），Web UI 用 `assistant_message` 覆写 `textContent` 正确收敛（`web/app.js:294`）。但**只消费 `text` 事件的裸客户端会看到拼接的重复文本**——建议在 RUNBOOK 的客户端契约里点明：必须以 `assistant_message` 为最终文本，不能只累加 `text`。

### 2.6 Artifact CAS 锁无死锁

`_verified_read`（共享锁）、`_durably_publish`（排他锁）、`_cleanup_orphans_sync`（排他锁）三个入口各自只在叶子层取一次锁，`*_locked` 内部**不再重入**——不存在"持共享锁再申请排他锁"的自死锁路径（flock 按 open file description 生效，若存在嵌套将必然死锁）。6 读 + 6 写并发各 20 轮实测 0.4s 完成，无死锁无饥饿。

### 2.7 存储与 schema

- `database.py` 实测四项 PRAGMA 齐备：`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、`busy_timeout`，写事务用 `BEGIN IMMEDIATE`——与规格 §9.4 完全一致
- `run_events` 有 `BEFORE UPDATE` / `BEFORE DELETE` trigger 强制 append-only
- `UNIQUE(run_id,seq)`、`uq_run_terminal_event` partial unique index 保证 terminal 唯一
- `runs` 上 `CHECK ((terminal_status IS NULL) = (terminal_payload_json IS NULL))`、`CHECK (terminal_status IS NULL OR state = terminal_status)`

## 3. 发现的问题

### F-1（P1，正确性）引用归属在多次检索时被交叉相乘

**位置**：`agent/runtime/adapters/sqlite/store.py:1240`（`_derive_citations_in_tx`）
配合 `agent/tools/knowledge_search.py:61`

**问题**：每次 `knowledge_search` 独立地把命中编号为 `n = 1..k`（`enumerate(chunks)`），编号**不跨调用全局唯一**。而 finalize 事务里的引用推导是：

```python
for marker in markers:            # 正文里出现的 [n]
    for row in rows:              # 本 Run 全部 committed knowledge_search
        for evidence in result["evidence_index"]:
            if evidence["n"] == marker: -> 生成一条 citation
```

于是正文里**一个** `[1]`，会对**每一次**检索各生成一条 citation。M 次检索 → 每个 marker 最多 M 条引用，且指向不同文档。

**证据 1 — 确定性复现**（两次检索分别命中 alpha / beta，正文只写一个 `[1]`）：

```text
count = 2
evidence_ids = ['ev-alpha', 'ev-beta']
doc_ids      = ['alpha', 'beta']
markers      = ['[1]', '[1]']
```

模型只标注了一个来源，却被归因到 **alpha 和 beta 两个不同文档**——其中一条是凭空捏造的归属。

**证据 2 — 真实系统复现**（`native_loop`，提示词要求做两次独立检索）：

```text
committed knowledge_search executions: 2
distinct [n] markers in the answer: [1, 2, 3]
derived citations: 6
  [1] -> ['kb-agent-loop', 'kb-agent-loop']      <-- 一个 marker 两条引用
  [2] -> ['kb-adk-overview', 'kb-adk-overview']
  [3] -> ['kb-rag-pipeline', 'kb-rag-pipeline']
```

**影响**：

- 直接冲击本次重构的能力声明"Citation 从已提交 EvidenceSet 和最终回答**确定性**生成"、"citation 可追溯到稳定 Evidence"。它确实是确定性的，但**归属是错的**。
- 单轮单检索时不可见；多轮 tool-use loop（`agent_loop` / `native_loop` 的常态）一旦发生第二次检索就必然触发。本次三引擎冒烟每个 Run 恰好只检索一次，所以没暴露——这也说明现有测试样本不足。
- `tests/reliability/test_evidence_citations.py` 只覆盖单次检索，因此 242 门禁全绿。

**修复方向**（择一）：

1. **推荐**：让 Tool Broker 在 `_commit_result` 里用 **Run 内单调计数器**重新编号，模型看到的 `hits[n]` 与写入 `evidence_index` 的 `n` 使用同一套全局序号。这样 `[n]` 在一个 Run 内天然唯一，推导逻辑不必改。
2. 或者在 `evidence_index` 里保留 `tool_execution_id` + 序号二元组，并让推导只匹配"模型当轮实际看到的那次检索"——需要额外记录 marker 与 tool_execution 的对应关系，复杂度更高。

建议同时补一条 reliability 测试：**两次检索 + 单个 marker → 恰好一条 citation**。

### F-2（P2，正确性）Evidence 的 span 偏移是伪造的，且可越界

**位置**：`arag/persistence/service.py:363`（`_make_version_chunks`）

**问题**：`span_start` / `span_end` 用累加游标推算：

```python
position = max(search_from, 0)
metadata.update({"span_start": position, "span_end": position + len(chunk.content)})
search_from = position + max(1, len(chunk.content))
```

但 chunk 内容来自 `Chunker`，它做了**段落切分 + `strip()` + 字符级 overlap**（`arag/components/chunker.py`）。所以 chunk 并不是原文在该偏移处的连续子串：分隔符被吃掉导致偏移持续漂移，overlap 又让真实区间互相重叠，而推算值是严格递增不重叠的。

**证据**（87 字符文档，`max_chars=40, overlap=8`）：

```text
span=(0,20)  match=True
span=(20,61) match=False
  chunk 内容      : '的持久化语义。\n第二段讨论 WAL 与 synchronous=FULL 的取舍。'
  document[20:61] : '\n\n第二段讨论 WAL 与 synchronous=FULL 的取舍。\n\n第三段说'
span=(61,99) match=False        <-- span_end=99 > 文档长度 87，越界
```

只有第一个 chunk 偶然正确；末块 `span_end` 甚至**超出文档长度**。

**影响**：Evidence / citation 里的 `span_start` / `span_end` 无法用于定位原文。任何按该区间高亮或摘录的消费方都会取到错误文本。规格 §10.10 把 `span` 列为 Evidence DTO 必备字段，changelog 也声称"Evidence 带完整 …/page/span/… 字段"——字段在，语义错。

**修复方向**：让 `Chunker` 在切分时**记录真实源偏移**并随 `Chunk` 返回（切分点本来就知道位置），`_make_version_chunks` 直接透传；在无法确定偏移的路径上宁可写 `NULL` 也不要写一个看似精确的错值。`page` 目前恒为 `NULL`（纯文本样本无分页），这是**诚实**的，可作为参照。

### F-3（P2，效率）Artifact 每次有界读取都全量重新哈希，图片物化呈平方级放大

**位置**：`agent/runtime/adapters/filesystem_artifact.py:454`（`_verified_read_locked` → `_hash_open_file`）
放大点：`agent/runtime/adapters/legacy_engines.py:185`（`_read_all`）

**问题**：每次 `read_range` / `read_bounded` 都对**整个 blob** 做一次 SHA-256 再切片。而多模态图片物化按 1 MiB 分片循环调用 `read_range`，于是 N 片 → N 次全量哈希。且哈希全程持有 CAS **共享 flock**，会与 publish 的排他锁竞争。

**实测**（20 MiB 图片附件）：

```text
artifact size   : 20 MiB
range reads     : 20
bytes hashed    : 400 MiB   (每次读都全量重哈希)
materialization : 1111 ms
amplification   : 20x
```

**影响**：单张 20 MiB 图片附件仅完整性校验就多花约 1 秒并 20 次抢锁；内部 Artifact 上限是 100 MiB，最坏情况更差。属于性能/锁竞争问题，不影响正确性。

**修复方向**：物化路径改为**一次开文件、单遍扫描**同时完成哈希与切片（或提供 `read_verified_stream` 一次性校验并流式返回）；HTTP Range 的逐次校验可保留，但同样建议单遍完成。

### F-4（P3，效率）BM25 检索对全库重复分词

**位置**：`arag/projection/snapshot.py:225`

```python
lexical_match = bool(query_set.intersection(_tokenize(snapshot.chunks[index].content)))
```

排序循环里对每个候选 chunk 重新 `jieba` 分词。而 `rebuild()` 第 127 行**已经算过** `tokens` 并用于构建 `BM25Okapi`，之后却丢弃了。命中稀疏时最坏会对整个语料重新分词一遍。

**修复方向**：把 `tokens` 一并存进 `ProjectionSnapshot`（它已是 frozen dataclass），检索时直接复用。

### F-5（P3，卫生）本地 `.env` 仍残留 R4 已删除的开关

实际 `.env` 中仍有：

```text
ENGINE = native_loop
EMBEDDING_STORAGE_DIR = local_storage/embedding
```

两者都是 R4 明确删除的旧语义（启动期主引擎选型、旧 embedding 权威路径），`.env.example` 已清理干净。`check.sh` 的 obsolete-protocol 扫描覆盖 `.env.example` 但**不覆盖 `.env`**（`.env` 被 gitignore，CI 也扫不到）。

因为 `AgentSettings` / `RagSettings` 都是 `extra="ignore"`，这两个键**无害**，不会导致启动失败。但它有误导性：有人可能以为改 `ENGINE=agent_loop` 还能切主引擎（现在 engine 是每 Run 必填的不可变字段，改它完全无效）。另外 `local_storage/embedding/` 目录仍在磁盘上。

**建议**：清理本地 `.env` 与 `local_storage/embedding/`；如果希望长期防回归，可让 `run_all.sh` 在启动前对 `.env` 做一次同样的过时键扫描并给出 warning（不必 fail）。

### F-6（P3，文档）幂等重放要求 `client_request_id` 同时保持稳定，但未写明

`AdmissionService.create` 的 `request_digest` 覆盖 `digest_payload()`，其中**包含 `client_request_id`**（`agent/runtime/application/admission.py:22-32`）。因此只固定 `Idempotency-Key`、每次重新生成 `client_request_id` 的客户端，重放会拿到 `409 IDEMPOTENCY_KEY_REUSE` 而不是原 Run。

我在写冒烟脚本时正好踩中这一点。设计本身合理（"同 key 不同 payload 即冲突"），但这是**客户端必须遵守的契约**，而 `README.md:105` 与 `RUNBOOK.md:183` 的示例 body 只给了一个 UUID 字面量，`RUNBOOK.md` 的错误码表也没写这条。

**建议**：在 RUNBOOK 的 CreateRun 小节加一句——重试同一请求时必须同时复用 `Idempotency-Key` 与 `client_request_id`；两者只要有一个变化就是一个新请求。

## 4. 设计层面的观察（非缺陷）

1. **`_derive_citations_in_tx` 放在 finalize 事务内做正则扫描 + 多行 JSON 反序列化**。当前规模没问题，但它违背了"写事务必须短"的自我约束的精神——引用推导是纯计算，理论上可以在事务外算好、事务内只写。目前 `[n]` 解析依赖已提交的 tool result，放在事务内可保证读到一致快照，属于合理取舍，但值得记一笔。

2. **`expire_deadlines` 绕过了 `_finalize_terminal_in_tx` 的 adjacency 校验**，直接 CAS 写 `TIMED_OUT`。CAS（`WHERE terminal_status IS NULL`）保证了 terminal 唯一，行为正确；但它是唯一一条不走状态机邻接表的 terminal 路径，未来改状态机时容易漏掉这里。建议加注释或让它复用同一校验。

3. **`RuntimeWorker._maintenance` 用 `getattr(self.store, "expire_deadlines", None)` 软探测**（`dispatcher.py:108`）。`RuntimeStore` 端口既然是显式契约，这里用可选属性探测会削弱端口的静态可检查性。建议提升为端口正式方法。

4. **Runs API 无任何认证/授权**：任何调用方可读写任意 `run_id` 的状态、事件、cancel、signal。这与规格 §4.3 明确后置"企业 IAM、跨租户治理"、CLAUDE.md 声明"无生产级多租户隔离"一致，**属于已声明边界而非缺陷**。但如果用于面试展示，建议主动提出这一点并说明单机单租户前提。

5. **`compile_history` 会纳入失败 Run 的用户消息**（只排除失败的 assistant 输出）。这符合规格"保留所有已提交用户消息"，但意味着下一轮上下文里会出现"用户问了、但没有任何回答"的悬空轮次。这是有意设计，建议在 `docs/reliability/` 里显式写清楚，避免以后被当成 bug 改掉。

## 5. 诚实边界确认

changelog §12 的能力边界表述**准确**，未发现夸大：

- 明确声明单机 SQLite + 本地磁盘，不宣称分布式 HA / 跨主机容灾 —— 属实

- 明确不承诺 provider token 级流重放 —— 一致
- 明确 Delivery v1 只承诺 committed/AVAILABLE，无服务端 ACK —— 与 `runs.py` 实现一致（cursor 完全在客户端）
- 明确 GraphStore 未接检索流、无 Memory、无 Context Compiler —— 一致

## 6. 建议处理顺序

| 优先级 | 项 | 理由 |
|---|---|---|
| 1 | F-1 引用交叉相乘 | 唯一影响对外正确性的缺陷，且必然在多轮检索触发 |

- 两次 `knowledge_search` + 正文单个 `[1]` → 恰好 1 条 citation
