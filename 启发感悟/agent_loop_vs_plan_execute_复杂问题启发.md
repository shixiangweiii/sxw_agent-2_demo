# agent-loop 与 plan_execute 在复杂问题上的启发

生成时间：2026-06-30

## 背景

在同一份 30 题受控考卷上，`agent_loop` 和 `plan_execute` 在简单题上几乎没有差异，中等题差距也很小；真正拉开差距的是复杂题。复杂题往往包含跨文档推理、多跳检索、工具调用、图片锚点召回、反问和矛盾信息处理。

这说明两类引擎的差异，不主要体现在“能不能做基础 RAG 问答”，而体现在复杂任务中是否能持续根据中间证据调整下一步动作。

## 核心判断

复杂问题需要的不是一次性“先计划再执行”的形式，而是持续的闭环控制：

```text
观察问题和已有证据
  -> 决定下一步
  -> 调用工具或检索
  -> 观察结果
  -> 判断证据是否足够
  -> 修正路线或继续补查
  -> 最终回答
```

`plan_execute` 的基本形态更接近：

```text
先制定路线 -> 按路线执行 -> 汇总回答
```

`agent_loop` 的基本形态更接近：

```text
看当前状态 -> 决定下一步 -> 执行 -> 再看结果 -> 再决定下一步
```

当问题变复杂后，`plan_execute` 如果要保持高质量，就必须引入观察、补检索、纠偏、重写计划、失败重试、证据覆盖检查等机制。随着这些机制增加，它会逐渐演化成一个带显式计划表的 `agent-loop`。

因此，二者不是完全割裂的两种范式，而更像一个连续谱：

```text
固定 workflow
  -> plan_execute
    -> plan + step retry
      -> plan + observe + replan
        -> planner-guided agent-loop
          -> free-form agent-loop
```

## 为什么复杂题会放大 agent-loop 优势

1. 复杂问题里的下一步经常依赖前一步检索结果，无法在开头完全规划清楚。
2. 多文档问题需要边检索边判断证据缺口，固定计划容易过早收束。
3. 复杂问题常同时要求事实、计算、引用和反驳，最终答案必须综合多个中间结果。
4. 当工具调用结果不完整时，`agent_loop` 更自然地继续补查；`plan_execute` 如果没有 replan 机制，容易带着缺口进入最终回答。
5. 跨文档 citation 覆盖不是简单的生成问题，而是证据管理问题；复杂任务需要显式维护“已经找到哪些证据、还缺哪些证据”。

## 对当前项目的启发

`plan_execute` 仍然有价值，尤其适合步骤明确、流程可控、需要强解释性的任务。但复杂开放问题中，计划不应该是铁轨，而应该是导航仪：它提供方向，但每一步都要允许根据新证据修正路线。

更理想的方向不是简单地二选一，而是构建一种 `planner-guided agent-loop`：

- 开始时生成高层计划，帮助模型明确任务结构。
- 每次工具调用后更新当前证据状态。
- 允许计划根据检索结果动态调整。
- 为多文档任务维护 evidence ledger，记录每个结论来自哪些文档和片段。
- 最终回答必须从 evidence ledger 中取证据和 citation，避免只答对内容但引用覆盖不足。

## 后续优化方向

1. 为复杂知识题增加“先检索再计算”的约束，避免模型只使用用户给出的数字直接计算。
2. 在工具层或运行时层维护 evidence coverage，提醒模型哪些 gold-like 文档或主题还没有被覆盖。
3. 给 `plan_execute` 增加 observe/replan 阶段，而不是只做一次性计划。
4. 将 `agent_loop` 的动态工具发现、text_stats 等工具面与 `plan_execute` 的可解释计划能力逐步对齐，减少评测时的工具面偏差。
5. 把复杂任务的最终回答拆成“结论、证据、引用、未确认信息”四个结构化部分，降低遗漏和幻觉风险。

## 一句话总结

复杂任务里，计划的价值不是把路径提前写死，而是帮助 agent 更好地循环；当 `plan_execute` 足够复杂时，它本质上会走向一个带计划约束的 `agent-loop`。
